# Data Change Plan

仅在方案涉及表、字段、索引、约束、历史数据或一次性执行脚本时读取。

## 先确定项目真实建表方式

不要通用化“新表自动创建”。先在目标仓库检查：

1. 模型是否在启动链路中完成注册。
2. 是否存在并实际调用 `create_all()`，以及调用前能否加载目标模型。
3. 是否使用 migration，以及新表/旧表变更的既有 migration 惯例。
4. 上线审批是否要求 DDL、migration 文件或脚本清单。

根据证据分别记录三个维度，不强制三选一：

- 代码定义：ORM 模型、schema 或其他结构定义位于哪里。
- 实际执行入口：生产环境最终由 `create_all()`、migration 或人工执行 DDL 中的哪一条创建/变更结构。
- 审批材料：是否需要提交 DDL、migration 文件或脚本清单。

ORM 定义、migration 执行和 DDL 审批可以合理组合，但生产上线的实际执行入口必须唯一明确，避免同一结构被重复执行。证据不足时标记“待确认”，不得写成无需脚本或无需审批。

使用规则：

- 多张新表或旧表均按表分组，不把字段混在一张总表。
- 状态、类型、来源等枚举值直接写入字段清单。
- 旧表只写实际变化；没有字段、索引或历史数据变化时省略对应小节。
- SQL 或脚本不要在数据影响说明和上线方案中重复粘贴。

审批清单规则：

- `ALTER`、索引调整、数据回填/清理、迁移和一次性脚本必须进入清单。
- 新表是否进入清单取决于已取证的创建方式和审批惯例，不做通用假设。
- “不需要”也要有仓库证据；证据不足时写“待确认”。
