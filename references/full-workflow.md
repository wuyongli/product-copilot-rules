# Full Product Workflow

仅在 `SKILL.md` 判定为完整模式时读取。正式顺序：

`Stage 0 → Stage 1 → Stage 2 → 用户确认 → Stage 3 → Stage 4 → Stage 4.5 → Stage 5`

## Stage 0：需求洞察与成立性

先把用户想法转换为可分析、可取舍、可验收的问题。

至少判断：

- 真实问题、触发原因、目标结果和受影响角色。
- 当前表述是目标、手段、补丁还是实现偏好。
- 当前现状与目标之间的差距。
- 验收口径、约束、收益、代价和关键矛盾。
- 建议动作：推荐做、不建议直接做、先验证或缩小范围做。

先给判断和理由，再列待确认假设与关键问题。若结论是不建议直接做或先验证，默认进入停止出口，不继续展开完整方案。

## Stage 1：需求澄清

只收集会改变需求成立性、范围、取舍或验收的信息。通常包括业务背景、目标用户、使用场景、成功标准、关键约束、历史方案和跨系统影响。

不要输出长问卷：先写当前理解与 AI 初步建议，再提出最少的问题。信息已经明确时可以直接进入 Stage 2。

## Stage 2：业务理解确认

用户在这里确认的是业务决策，而不是未经取证的技术机制：

1. 业务目标和核心流程。
2. 需求为什么成立。
3. 推荐取舍及原因。
4. 建议纳入与不纳入范围。
5. 验收口径。

前后端影响、数据结构、权限、外部依赖、迁移和上线方式可以给初步判断，但标记为“待 Stage 3 取证”，不要求用户确认 ORM、migration、DDL 等实现机制。

等待用户确认上述业务决策后进入 Stage 3。模板见 [output-templates.md](output-templates.md)。

## Stage 3：当前系统现状评估

围绕已确认业务范围做定向取证：

- 判断主改仓、配套仓和职责边界。
- 检查现有业务能力、交互/接口、调用链路、数据结构、权限、配置和发布链路。
- 检查兼容旧逻辑、旧数据、旧客户端和旧流程的要求。
- 查找相似功能、测试和历史实现，判断复用、局部改造、增量扩展或结构性重构。
- 识别改造成本最高和风险最大的部分。

输出仓库判断、证据位置、已有能力、主要约束、可复用部分以及推荐改造路径。

如取证推翻 Stage 2 判断：

- 明确写出“原判断 → 新证据 → 调整建议”。
- 只有业务范围、取舍或验收发生变化时才请求用户确认变化部分。
- 纯技术落点调整直接进入方案，不重复确认业务结论。

涉及数据变化时读取 [data-change-plan.md](data-change-plan.md)。

## Stage 4：结构化产品方案

进入条件：需求建议为推荐做或缩小范围做，主改仓已明确，关键业务边界和系统约束足以支持方案。

使用 [plan-template.md](plan-template.md) 选择种子版或正式版：

- 固定核心章节必须覆盖。
- 条件章节只在影响方案、实现或验收时展开。
- 不适用章节直接省略，不写空标题或“无”占位。
- 先写推荐方案；备选方案只在仍有真实取舍时保留。
- 未确认内容显式标记，不得伪装成事实。
- 当前阶段不推进的模块只保留范围边界或导航。

如果仍有重大待确认事项，继续更新种子版，不提前铺满正式结构。

## Stage 4.5：开发方案

当产品方案已基本确认、用户询问怎么开发或准备进入实现时展开。

- 按业务改动点或依赖阶段组织，不机械拆成前端/后端清单。
- 每个改动点说明目标、主改仓、配套仓、接口、数据、权限/配置、兼容和验证。
- 说明复用能力、新增能力、关键实现路径和不推荐路径。
- 仅在确有公共数据层、服务层或接口层前置改造时单列基础层。
- 非当前阶段模块不展开实现细节。

产品方向已确认不等于允许编码。进入代码前仍需用户明确授权。

## Stage 5：自检与风险披露

检查：

- 是否仍有会改变方案的假设或边界。
- 问题定义、目标、范围与验收是否一致。
- 方案是否基于真实系统证据并复用已有能力。
- 数据、权限、兼容、上线、回滚和监控是否按需覆盖。
- 是否区分事实、建议和待确认项。
- 开发方案和开工授权是否满足。

只输出发现的问题及风险等级；无问题时简短说明通过，不重复完整清单。

## 停止出口

以下任一条件成立时不进入正式方案：

- 需求不建议直接做或应先验证。
- 关键业务事实不足，无法判断需求是否成立。
- 主改仓不明确，系统评估基础不成立。
- 当前系统约束不支持短期推进。

输出当前结论、停止原因、已有证据和最小下一步。模板见 [output-templates.md](output-templates.md)。
